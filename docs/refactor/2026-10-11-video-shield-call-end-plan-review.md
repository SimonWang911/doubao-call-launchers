# AI通话遮罩与通话结束重构计划开发前 Review

> 历史记录：当前设计以 [2026-10-13 前台会话重构](2026-10-13-foreground-session-refactor-plan.md) 为准，以下为已废止双击方案的 Review 证据。

## 1. Review 对象和依据

- Review 对象：`docs/refactor/2026-10-11-video-shield-call-end-refactor-plan.md`。
- 真实代码依据：当前 `TouchShieldService.java`、`CallLauncherActivity.java`、两个 Manifest、`RuleRepository.java`、现有 PowerShell 门禁和临时通知探针源码。
- Review 边界：只审查计划、接口和测试门禁，不修改业务代码；业务开发必须等本 Review 的 P1 问题关闭。

## 2. 独立审查发现

### P1：通知监听“已授权”与“已连接”必须分开

计划如果只检查系统设置中的授权，就可能在监听器尚未绑定时打开语音或视频，双击后却没有通话结束能力。

**修订结果：**复核后将“授权”和“连接”分成两个门槛：启动器仍要求通知读取授权已开启，但 `RESULT_READY` 只依赖前台服务和遮罩窗口成功挂载。监听服务异步重绑；双击发生在未连接阶段时返回 `UNAVAILABLE`、进入 `END_FAILED` 并保留遮罩，连接恢复后可重试。这样不会把荣耀 ROM 的连接延迟误报为语音或视频保护启动失败。

### P1：点击 PendingIntent 不能直接视为挂断成功

`RemoteViews.performClick()` 只说明 View 接受了点击，不等于豆包已经结束通话。

**修订结果：**计划已增加目标通知移除/无其他可验证挂断通知的确认条件；通知未消失、控件缺失、异常和超时全部进入失败状态，遮罩不清理。

### P1：不能把探针中的开放广播复制进正式 APK

临时探针的导出广播是测试入口，不适合作为正式控制接口，可能被其他应用任意触发。

**修订结果：**正式方案只允许同进程 `CallEndCoordinator` 调度系统绑定服务；通知监听服务不增加外部广播控制入口，Manifest 只注册系统要求的绑定 Intent。

### P2：固定通知 ID 会造成版本回归

荣耀当前通知 ID 为 101，但豆包更新后可能变化。

**修订结果：**计划将 101 降级为候选优先级，主条件改为固定豆包包名和可验证 `hangup_btn`/明确挂断 Action；无证据不点击。

### P2：遮罩文本子 View 可能造成触摸穿透或事件分裂

只给 TextView 设置背景不能证明全屏触摸仍被消费。

**修订结果：**计划要求根容器拦截完整触摸序列，提示子 View 不得穿透，并保留 `FLAG_NOT_TOUCHABLE` 禁止门禁；真机测试覆盖单击和滑动。

### P2：纯静态字符串测试不能证明双击和视觉

**修订结果：**计划增加无 Android 依赖的确定性双击测试，以及真实设备截图/UIAutomator/通知和 Activity 证据；明确结构门禁不能替代真机验收。

### P1：现有 `START_STICKY` 空 Intent 路径会绕过会话协调

当前服务收到 `null` Intent 时会重新创建遮罩并返回 sticky；系统重启服务时没有有效的豆包 Intent、结果接收者或通话会话，可能留下孤立遮罩。

**修订结果：**计划增加 action 校验和 null/未知 Intent 负例；有效会话返回 `START_NOT_STICKY`，无有效启动 Intent 立即清理并停止服务。

## 3. 调用方、数据流和接口复核

- `CallLauncherActivity` 是唯一语音/视频启动编排者，保留规则、音量、模式和 Intent；新增的是两个模式共同使用的通知监听授权预检和遮罩服务启动门禁。
- `TouchShieldService` 是唯一悬浮窗拥有者，不直接解析豆包通知，不直接执行清理以外的通话控制。
- `DoubaoNotificationListenerService` 是唯一系统通知适配者，只处理固定豆包包名。
- `CallEndCoordinator` 是唯一结束请求协调者，避免 View、通知服务和 Activity 各自维护结束状态。
- `AI语音` 和 `AI视频` Manifest 都注册新增服务；共享源码、Manifest 和 Activity 三者共同保证两个 APK 使用同一保护链路。
- 远程规则只提供已校验的豆包入口，不携带通知资源名、权限开关或遮罩行为，避免把外部 UI 细节变成远程执行配置。

## 4. 测试门禁复核

计划覆盖了以下开发前失败证明：

1. 旧代码没有纯 Java 双击类，双击边界测试应先失败。
2. 旧的两个 Manifest 都没有通知监听服务，双 APK 服务注册门禁应先失败。
3. 旧遮罩没有半透明背景、提示文字和结束协调调用，遮罩契约应先失败。
4. 旧代码没有挂断确认状态，通知适配/失败保持门禁应先失败。
5. 旧服务对 null Intent 的 sticky 恢复没有会话依据，生命周期负例应先失败。

测试执行顺序固定为：纯 Java 时间模型 -> 结构契约 -> 编译 -> APK 构建/签名 -> ADB 安装与授权 -> 真实视频/语音场景。任何前置阶段失败都不得用后续真机结果掩盖。

## 5. 最终审查结论

- 未发现需要重新开发两个 APK 或重做远程规则体系的问题。
- 高优先级问题已通过“两个 APK 共用通知监听服务 + 结束协调层 + 可测试双击状态机 + 挂断结果确认 + 失败保持遮罩”在计划中闭环。
- 计划没有引入与需求无关的数据库、无障碍、设备所有者或大型框架。
- 允许进入测试先行阶段；在测试先行门禁完成前，不得修改业务 Java 或 Manifest。
