## 2. 当前真实架构与证据

### 2.1 已存在的正确链路

1. `CallLauncherActivity` 读取模式、拉满媒体和通话音量、等待 `RuleRepository` 返回规则，并按规则构造豆包 Intent。
2. 语音和视频模式都先检查悬浮窗和通知可见性，再通过 `TouchShieldService` 建立前台服务和悬浮窗；收到 `RESULT_READY` 后才调用 `startActivity()`。
3. `TouchShieldService` 独立于启动 Activity，能够在 Activity 退出后保持窗口和前台通知，并通过通知动作移除自身遮罩。
4. 语音和视频 Manifest 都注册 `TouchShieldService` 与 `DoubaoNotificationListenerService`，两条入口共用同一套通话保护能力。
5. 规则链路仍固定豆包包名 `com.larus.nova`，未把遮罩行为放进远程规则。

### 2.2 当前代码事实

- `TouchShieldService.java:23` 将自身定义为透明、消费触摸的窗口服务。
- 基线提交 `3a95e98` 的 `TouchShieldService.java:243-254` 中 `ShieldView` 使用透明背景，只有 `setClickable(true)` 和 `onTouchEvent() -> true`，没有文本、半透明绘制或点击状态机。
- `TouchShieldService.java:124-145` 的通知动作只调用 `ACTION_STOP`，当前语义是“解除遮罩”，不会结束豆包通话。
- `CallLauncherActivity.java:121-177` 只编排遮罩就绪，未编排通话结束控制。
- 基线提交 `3a95e98` 的两个 Manifest 都没有 `NotificationListenerService`；当前实现已把该组件和遮罩服务声明同步到两个 APK。
- 主仓库搜索不到 `NotificationListenerService`、`BIND_NOTIFICATION_LISTENER_SERVICE`、`RemoteViews`、`hangup_btn` 或 `performClick` 的正式实现。
- 现有 `verify_touch_shield.ps1` 只验证遮罩服务、权限、READY 顺序和触摸消费，不能证明视觉效果、双击识别、豆包挂断或挂断失败时的状态保持。

### 2.3 已验证但尚未产品化的通知挂断证据

临时探针 `work/doubao-notification-probe` 在荣耀 `NTH-AN00`、豆包 `com.larus.nova` 版本 `14.9.0` 上验证了以下事实：

- 豆包通话通知的标准 `Notification.actions` 为空。
- 通知使用自定义 `RemoteViews`，其中存在资源名 `hangup_btn`。
- 以豆包包名创建上下文，应用 `contentView`/`bigContentView` 后找到 `hangup_btn`，调用其 `performClick()` 可以触发豆包自己的挂断 `PendingIntent`。
- 语音和视频通话均已实测结束，`RealtimeCallActivity` 退出且通话通知消失。

这证明了当前设备和该版本上存在可由普通 APK 通过通知监听授权使用的入口，但不证明豆包所有版本、所有 ROM 永远保持相同通知布局。因此该能力必须封装成可失败、可观测、可替换的适配器，不能散落在遮罩 View 中，也不能把 `notificationId=101` 当作唯一契约。

## 3. 已确认问题

### P1-1：遮罩没有结束通话能力

当前双击无论如何都不会结束豆包通话，因为遮罩 View 只消费事件，服务的唯一停止路径是移除自身窗口。通知“解除遮罩”也只停止 `TouchShieldService`。如果直接增加一个计数器，最多只能关闭遮罩，不能满足“结束当前状态”。

### P1-2：缺少普通 APK 可用的通话控制边界

主工程没有通知监听服务，也没有任何调用豆包挂断 PendingIntent 的代码。ADB、`forceStopPackage`、直接杀进程、坐标点击和无障碍服务都不能作为正式应用内核心路径：它们要么不属于 APK 权限，要么依赖易失的额外授权，要么会粗暴终止整个豆包进程。

### P1-3：没有授权、连接和结果确认状态

通知读取授权与 `POST_NOTIFICATIONS` 是两项不同能力。基线代码只检查自己的通知是否可见，没有检查通知监听授权，也没有处理监听服务断开、重新绑定、挂断点击未找到或点击后通话通知未消失的情况。若只收到 `performClick()` 返回值就关闭遮罩，可能出现“看似结束，实际通话仍在”的半保护状态；该缺口会同时影响语音和视频。

### P1-4：没有双击状态机，无法定义误触边界

当前所有触摸都直接返回 `true`。新增需求要求两次有效点击在 3 秒内完成，且无最小间隔；还必须保证单击、滑动、长按和一次触摸序列不会触发结束。需要独立、可测试的时间窗口和触摸序列状态，而不是在 `onTouchEvent()` 中堆叠条件分支。

### P2-1：现有视觉实现与新需求相反

当前窗口和 View 都是透明的，用户看不到遮罩状态，也没有大字提示。README 和历史计划仍描述“透明遮罩”和“没有面向老人的解锁触摸手势”，需要在开发完成后同步更新，避免文档与行为冲突。

### P2-2：测试门禁覆盖不到新行为

现有静态门禁通过只能证明旧遮罩结构存在。它不能证明：半透明像素确实存在、提示文字显示、双击窗口正确、非双击不结束、通知监听只处理豆包通话通知、挂断成功后遮罩清理、失败后遮罩继续拦截，以及荣耀/小米上的真实结果。

## 4. 根因判断

本轮问题的统一根因是：`TouchShieldService` 目前同时承担了“悬浮窗承载”和“用户结束通话后的收尾”这两个不同层次的职责，但工程没有独立的通话控制端口。遮罩只能控制自己的窗口，无法触达豆包内部通话状态；同时，触摸事件、通话结束请求和服务清理没有共同的会话状态机。

半透明和提示文字是表现层缺口，双击识别是输入层缺口，通知监听挂断是外部系统适配层缺口。它们应通过一个会话协调层连接，不能分别在 `ShieldView`、通知动作和 Activity 中各写一套结束逻辑。

## 5. 技术路线比较

| 路线 | 结论 | 原因 |
| --- | --- | --- |
| ADB、`forceStopPackage`、直接杀进程 | 不采用 | 不是普通 APK 可授予的运行时能力；即使能执行，也会粗暴终止整个豆包进程，不等价于挂断当前通话。 |
| 无障碍服务点击挂断 | 不采用 | 依赖用户长期授权，荣耀等 ROM 可能重置；还需要识别布局或坐标，维护成本和盲人使用风险高。 |
| 设备管理员、设备所有者或 Kiosk | 不采用 | 不能直接取得豆包挂断 PendingIntent，部署会改变整机管理方式。 |
| 在遮罩上模拟豆包按钮坐标 | 不采用 | 触摸被遮罩消费后，事件不会穿透到豆包；普通 APK 也不能代替系统向其他窗口注入触摸。 |
| 只关闭遮罩或只停止本 APK 服务 | 不采用 | 豆包通话仍然可能继续，不能满足结束当前通话。 |
| `NotificationListenerService` + 豆包通话通知自定义 `RemoteViews` | 采用 | 已在荣耀设备实测可触发豆包自己的挂断 PendingIntent；属于系统提供给用户授权的通知通道，不依赖 ADB 或无障碍。必须加入固定包名过滤、候选布局探测、结果确认和失败保持遮罩。 |

## 6. 最优重构方案

### 6.1 目标架构

```text
AI语音/AI视频 CallLauncherActivity
  -> 拉满音量、加载规则、检查悬浮窗/通知/通知监听授权
  -> 请求 CallEndCoordinator 建立对应模式的受保护通话会话
  -> TouchShieldService 建立半透明窗口和前台通知
  -> NotificationListenerService 确认已启用并可连接
  -> 两项能力都 READY 后打开对应的豆包语音或视频入口

TouchShieldService
  -> 只负责前台服务、悬浮窗、提示 View、触摸消费和会话清理
  -> DoubleTapDetector 在 3 秒窗口内识别两次有效点击
  -> 第二次有效点击交给 CallEndCoordinator
  -> ENDING 期间继续消费触摸，不提前移除遮罩

DoubaoNotificationListenerService
  -> 只负责系统通知监听和豆包通知适配
  -> 仅处理固定包名 com.larus.nova
  -> 优先识别标准挂断 Action；无标准 Action 时探测 content/big/heads-up RemoteViews
  -> 通过资源名 hangup_btn 找到挂断控件并执行其自身点击回调
  -> 观察目标通话通知消失或挂断控件消失后回传成功

CallEndCoordinator
  -> 管理 READY、ACTIVE、ENDING、ENDED、END_FAILED 状态
  -> 串联遮罩和通话控制，阻止重复结束请求
  -> 只有确认通话结束后才清理遮罩；失败或超时保持遮罩并保留家人通知入口
```

### 6.2 模块职责和接口边界

#### `TouchShieldService`

- 保留现有独立前台服务生命周期和 READY/FAILED 回执。
- 将根 View 改为可布局容器：全屏使用低到中等透明度的深色背景，中心显示高对比度大字提示“**双击屏幕，结束当前通话**”。提示必须在横竖屏和常见字体缩放下不裁切。
- 使用 `FrameLayout`/自定义容器拦截全部触摸，不设置 `FLAG_NOT_TOUCHABLE`；提示子 View 不得让事件穿透。
- 双击成功只发出结束请求，不直接移除窗口。
- 结束成功、家人显式停止、服务销毁和启动失败都进入统一清理路径。

#### `DoubleTapDetector`

- 建议作为无 Android 依赖的独立纯 Java 类，使用注入时间或 `long now`，便于确定性测试。
- 只把两个完成的点击算作有效点击；滑动超过 touch slop、`ACTION_CANCEL`、长按未完成或超过 3 秒都重置窗口。
- 第二次有效点击的时间差 `<= 3000ms` 即触发；不增加额外最小间隔。
- 触发后立即进入一次性锁定，直到协调层返回结果，避免一次双击发送多个挂断请求。

#### `CallEndCoordinator`

- 不把结束逻辑写在 `ShieldView` 或 `CallLauncherActivity` 中。
- 维护当前 AI语音或 AI视频会话和一次性结束请求；向遮罩提供 `requestEnd()`，向通知适配器提供回调。
- 结果分为 `SUCCESS`、`ALREADY_ENDED`、`UNAVAILABLE`、`NOT_FOUND`、`TIMEOUT`、`FAILED`，其中成功和已结束才允许移除遮罩。
- 不执行 ADB、进程杀死、系统设置写入或跨应用坐标点击。

#### `DoubaoNotificationListenerService`

- 在两个 APK 注册，使用系统要求的 `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` 服务权限和 `android.service.notification.NotificationListenerService` Intent action；服务必须由系统绑定，不能开放任意外部调用。
- 只接受 `com.larus.nova` 的活动通知，不记录通知正文或敏感内容。
- 不把通知 ID `101` 作为唯一条件；固定包名 + 可验证通话控件是主选择条件，`101` 只能作为当前版本的优化提示。
- 按 `contentView`、`bigContentView`、必要时 `headsUpContentView` 顺序尝试，应用豆包上下文后查找 `hangup_btn`。所有 `RemoteViews` 异常都转为失败结果，不能导致服务崩溃。
- 如果未来出现标准 `Notification.Action` 且能通过标题/资源证据确认是挂断，允许把标准 Action 作为优先适配器；不能因为存在任意 Action 就盲目点击。
- 执行点击后等待目标通知移除或明确不再包含挂断控件。超时不报告成功，遮罩继续存在。
- 监听服务断开时主动标记不可用，必要时通过公开的 `requestRebind()` 请求系统重新绑定；不能修改系统授权状态。

### 6.3 会话状态和失败策略

| 状态 | 允许动作 | 结果 |
| --- | --- | --- |
| `STARTING` | 等待遮罩和通知监听能力就绪 | 任一能力失败则不打开豆包 |
| `ACTIVE` | 消费全部触摸；双击发起一次结束请求 | 进入 `ENDING` |
| `ENDING` | 继续消费触摸；忽略重复双击 | 等待通知适配器确认 |
| `ENDED` | 清理遮罩、前台通知和会话 | 豆包挂断入口已确认结束 |
| `END_FAILED` | 保留遮罩和家人“解除遮罩”通知动作 | 允许下一次重试；不假报已结束 |
| `STOPPED` | 释放窗口和服务资源 | 只在显式家人解除、启动失败或确认结束时进入 |

通知监听授权未启用，或者在启动阶段无法建立可用的结束控制能力时，语音和视频入口都按“失败关闭”原则不打开豆包。通话中监听暂时断开时不能保证自动挂断，系统应保留遮罩，不自动解除保护；家人仍可通过现有通知动作解除遮罩。

### 6.4 既有规则与音量链路的兼容边界

- 不新增远程规则字段，也不允许远程 JSON 改变通知监听目标包名、资源名或结束策略。
- 固定包名继续由代码校验为 `com.larus.nova`；通知适配器同样固定过滤该包名。
- 规则加载继续遵守缓存存在最多等待 2 秒、无缓存最多等待 10 秒，迟到结果只更新缓存，不触发第二次豆包启动。
- `maximizeAudibleVolume()` 和语音/视频成功短播报不改动。
- AI语音和 AI视频都注册遮罩与通知监听服务，都要求一次性完成悬浮窗、通知和通知监听授权；两者的规则入口、音量拉满和短播报逻辑保持原有差异。

## 8. 开发前门禁和分阶段计划

### 阶段 0：本 Review 收口

- 修改位置：本 Review 文档和后续重构计划文档。
- 禁止：修改业务代码、Manifest、规则、版本和设备状态。
- 完成标准：根因、路线、失败策略、权限和验收证据边界明确。

### 阶段 1：测试先行

- 新增纯 Java `DoubleTapDetector` 测试入口和通知选择器/结果状态测试；扩展 `verify_touch_shield.ps1`，增加半透明、提示文本、3 秒常量、结束协调调用和失败保持遮罩契约。
- 扩展项目门禁：两个 Manifest 都注册通知监听和遮罩服务；禁止出现 ADB、`forceStopPackage`、`FLAG_NOT_TOUCHABLE` 等实现路径。
- 在旧代码上确认新增回归测试因缺少真实能力而失败，不能只写“字符串存在”测试。

### 阶段 2：结束控制基础抽象

- 新增 `CallEndCoordinator`、`DoubleTapDetector` 和通知适配结果模型。
- 先完成状态转移和时间边界，再接 Android 服务；不改远程规则、音量和豆包 Intent。
- 完成标准：纯 Java 测试覆盖成功、超时、重复请求、滑动、长按、恰好 3 秒和超过 3 秒。

### 阶段 3：通知监听适配器

- 新增两个 APK 共用的 `DoubaoNotificationListenerService` 和可测试的通知候选选择逻辑，修改两个 Manifest 和共享启动授权预检。
- 只使用公开 Android API、固定豆包包名和已验证的 RemoteViews 证据；不保留临时探针的导出广播入口。

## 9. 风险、回滚和明确边界

- 豆包通知布局属于外部实现细节，`hangup_btn` 可能改名或被移除；适配器必须失败关闭，不得误点其他通知。规则 JSON 不适合承载此类 UI 资源名。
- 通知监听权限能读取设备通知，必须由家人明确开启；应用不绕过系统授权、不写系统设置、不保存通知内容。
- 荣耀/小米可能断开或延迟重绑通知监听；断开时继续保留遮罩，不假报成功。若启动阶段无法确认能力，则不打开任一通话入口。
- 半透明遮罩不能阻止 Home、系统返回手势、锁屏、通知栏或系统级语音助手；它只保护豆包通话内容区域。
- “结束豆包通话”不等于“杀死豆包进程”。正式验收以豆包通话结束、通话通知消失/无挂断控件、`RealtimeCallActivity` 退出和本 APK 服务清理为准，不要求也不尝试强制终止整个豆包进程。
- 回滚顺序：先撤回两个模式对通知监听能力的强制依赖，再删除通知监听服务和结束协调层，最后恢复遮罩旧 UI；不重置工作区、不覆盖无关修改。

## 10. 当前 Review 结论

当前架构可以继续重构，不需要重新开发两个 APK，也不需要改远程规则体系。最小且完整的根因修复是：保留共享前台悬浮窗服务，引入共享通知监听适配器和结束协调层，把双击识别做成独立可测试状态机；两个 APK 的遮罩只有在豆包挂断结果确认后才清理。该路线覆盖语音和视频，保留远程规则、强制拉满音量和各自入口播报。
